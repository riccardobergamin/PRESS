Research pipeline

The procedural research code is organized in pipeline/, separately from the inference package PRESS/. It prepares the observations, fits the five components, composes held-out h and xLoss, and produces the descriptive reports. This page gives the reading order, dependencies and input/output layout.

Download the research pipeline · Source and reading guide · Distributed objects · Roadmap

The archive contains the pipeline/ source tree, documentation and split/grid protocols. It prepares task inputs from public SkillCorner match files and connects each fitted stage to its downstream tasks. Match data and fitted fold objects are generated during execution; the package supplies the final pretrained inference models.

Numbered workflow

The execution plan prints the commands in dependency order. The task scripts retain the same simple organization: definitions of covariates or likelihood, training and validation, then a pipeline that executes those steps.

Step Component Reading order
01 Preprocessing Preparation → pipeline. Tracking derivatives and segmentation are in tracking.py; pass links are in passes.py.
02 Expected threat Model → training → pipeline.
03 Physical ball-drive risk Model and priors → training → pipeline.
04 CatBoost ball-drive comparison Features → training → pipeline.
05 Pass probability Physical model → training → pipeline.
06 Pass selection, flat and cross-nested Features → training → pipeline.
07 Action selection, then residual risk Features → training → pipeline.
08 h, xLoss and band evaluation Composition → scores and bootstrap → pipeline.
09 Possession patterns and reports Classification → scores → real-frame cases → pipeline.
10 Statistical summaries Parameter and performance tables.

Flat and cross-nested pass selection share their feature calculation. Action selection and residual risk also share feature definitions, but their models, labels and outputs remain separate. The physical ball-drive model remains the deployed one; CatBoost is a benchmark comparison.

Modelling choices

Two considerations guide the choice of models. The analysis rests on ten matches, which favours simple models with few parameters. The project is also a research project, and in several components an exploratory choice was preferred to the search for the best predictive performance.

More complex architectures, such as the graph neural networks that SkillCorner uses for xLoss, would probably require a dataset of a different scale. This is a hypothesis based on the scale of the datasets typically used for such models; no feasibility study has been carried out.

Each model stores feature tables or physical arrays separately from fold fits, scores and production refits. Saved trees, spline bases, posterior quantities and calibration objects have explicit task folders. The pipelines preserve completed outputs; a fresh pipeline execution should use a new output root. The input/output guide describes the individual files.

The raw-data adapter reads the public SkillCorner match files. Shared preprocessing retains the broad observations and quality flags; task-specific outcome filters remain beside the task. Reconstructed task cohorts are saved under outputs/preprocessing/task_inputs/. Segmentation and context-label meanings are explained in the User guide.

Dependencies between models

Fold-specific feature builders receive explicit upstream model artifacts from the matching split. Held-out evaluation uses the models of the matching split. The handoff code exports completed physical, xT and choice fits into outputs/preprocessing/task_inputs/<task>/upstream/fold_<f>/; production counterparts are under upstream/production/. It checks the six-fitting/two-validation/two-test match roles before downstream feature extraction.

For the six-fitting/two-validation/two-test tree-model splits, physical and xT features use the matching fitting data; pass-completion and pass-selection calibration retain their declared validation roles. Residual-risk training uses cross-fitted P(carry); validation and test use the corresponding main action-selection model. Production residual training uses the five eight-fit/two-held action fits. The general benchmark and individual benchmark pages describe these procedures.

BCOS quantities used in the accepted benchmarks and pretrained classifiers come from the preliminary formulation with effective hazards. The transport-with-killing formulation is implemented and is the default for standalone BCOS calculations. Downstream retraining with this formulation remains planned. The training pipeline and pretrained classifiers preserve the preliminary benchmark feature definition.

For pass probability, the released source preserves the benchmark’s selection of one trajectory estimator per fitting split. It prepares both candidate paths, compares their reconstruction errors on the fitting matches, and uses the selected method for that fit. The pass-probability guide explains the procedure.

Composed risks, bands and reports

The composition stage produces one held-out h and xLoss per verified canonical checkpoint, using the models of the fold in which the match was held out. It combines the held-out predictions of the components.

  • Overall h/xLoss metrics and calibration use 15,085 verified-outcome states.
  • Bands, possession patterns and player/team reports use 14,919 states from 7,265 possessions with terminal canonical-action coverage.
  • Band intervals resample whole matches, with 2,000 replicates, fixed predictions/thresholds and seed 20261030. Empty and nearly empty bands are checked explicitly.
  • Player/team E−O scores resample whole individual possessions. The reports also provide pattern shares and exposure/retention summaries with their stated denominators.
  • Case studies retain real match/possession keys and use the package’s frame plotting function. A later verified control illustrates the outcome without adding a canonical checkpoint.

Details and results are in the composed-risk benchmark and the pressure report.

Local checks

The verification plan covers syntax and command-line entry points, reconstruction of a real match, physical calculations, short model fits, serialization, composition, metrics and report counts. The check guide explains their scope.

For pass selection, the short real-data check retains the complete destination grids for ten observed passes. It exercises flat/CNL likelihoods and gradients, the declared curvatures, reduced screening, tree and nesting updates, early stopping, temperature scaling, held-out scoring, feature importance and model export.

# Print the ordered research commands without executing fits.
python pipeline/00_pipeline.py --output-root /path/to/new_run

# Print checks; add --execute to run selected checks.
python pipeline/checks/run.py --output /path/to/new_checks

Release contents

The release script uses an explicit file allowlist. Alongside the source code, the site exposes statistical summaries of physical parameters, performance/calibration, bands and selected case-study/report tables. Full input tables, feature matrices, fold boosters, posterior objects and bootstrap replicates stay outside the release, and pretrained inference models are distributed with the PRESS package.
